# Contributing

Thanks for helping. This file explains how the repository is organized and
what a good change looks like.

## Where things live

```
magpie.zip               the skill folder, zipped for download (generated)
adapters/skill/magpie/   the skill folder people install (generated)
adapters/generic/        one long prompt for any other assistant (generated)
adapters/claude|chatgpt|gemini|copilot/   setup notes per platform, with what was checked and when
core/                    everything Magpie knows, in plain Markdown (edit here)
tools/                   the build script, the quote, count and evidence checks, the Word and Excel export, and the example deck builder
.github/workflows/       runs tools/check.py on every pull request
evals/                   test scenarios with planted problems, fixtures and run notes
docs/                    design, provenance, contributing, prompt style, changelog
docs/examples/           a filled-in report and readout (Markdown, Word, PowerPoint)
```

- `core/` is the only place research content is written by hand. Everything a
  researcher reads or uses comes from here.
- `adapters/skill/`, `adapters/generic/`, `.claude/skills/` and `magpie.zip`
  are generated by `tools/build.py`. Don't edit them directly; your change
  will be overwritten on the next build.
- `evals/` holds test scenarios. A change to a standard or a stage should come
  with a scenario that would catch it regressing.
- `docs/` holds the design, the provenance record and this file.

## Where Magpie stands

As of October 28, 2026.

- **Tested in Claude Code only.** Claude.ai, ChatGPT, Gemini and Copilot
  haven't been tested from start to finish; their setup steps come from
  each company's help pages.
- **Evals.** There are 122 test scenarios in `evals/scenarios/`. Most of
  the first 36 passed, but that run didn't prove Magpie was loaded each
  time. Later runs used stricter rules: 6 of 7 coaching scenarios and 7 of
  8 HEARTS scenarios (Loosbrock, K. (2025). The HEARTS Framework: Six
  lenses for evaluating AI-assisted UX research. Hey Kaleb & Co.
  https://www.heykaleb.com/hearts-framework) passed, with one partial
  each, and the diary capture
  scenario passed. In a test of drafting too early, none of the 12 runs
  after the fix drafted before the required answers were in. Many newer
  scenarios haven't been run live yet, including the ones for confidence
  and priority, choosing a method, and spelling and dates. All results so
  far were judged by a model, not yet by a person. Details are in
  `evals/runs/` and `evals/README.md`.
- **Standards.** Magpie follows 137 standards in `core/standards/`. 65 cite
  a public source, at least in part, such as the ICC/ESOMAR code, Braun
  and Clarke, or Nielsen Norman Group. The others are marked practitioner
  judgment. Every source is listed in `docs/PROVENANCE.md`.

## Files for assistants without skills

The README sends most people to `magpie.zip`. For other setups:

- `operating.md` in the zip is the rulebook (about 39,000 characters).
  Pasted as project instructions, with the other `.md` files added as
  knowledge, it runs Magpie in Claude.ai or ChatGPT Projects.
- `adapters/generic/system-prompt.md` holds all of Magpie in one file, for
  tools that take one very long system prompt, such as some API setups.
  It's about 330 KB, and `system-prompt-lean.md` is about 180 KB. Most
  custom-instruction boxes in chat apps are far smaller and will refuse
  both. Don't paste it into a Claude.ai project that already has the
  files; it repeats them.
- If you make your own zip, zip the files inside `adapters/skill/magpie/`,
  not the folder itself. Copilot needs `SKILL.md` at the top.
- The quote, count and evidence checks can be run by hand with Python, for
  example `python3 adapters/skill/magpie/scripts/count_check.py findings.md`.

## Credit lines

Magpie is MIT licensed, and copies must keep the copyright notice and the
license text. `tools/build.py` adds a credit line to the top of `SKILL.md`
and both system prompts, the foot of every method guide, template and other
file, and the top of each script, and copies `LICENSE` into
`adapters/skill/magpie/` and `adapters/generic/`. Keep this when changing
the build.

The people behind Magpie's rules get credit too. The build turns the
source table in `docs/PROVENANCE.md` into `sources.md` (code, authors,
year, title, link), ships it in the skill folder, `magpie.zip` and both
generic prompts, and points every mention of `docs/PROVENANCE.md` in the
built files at it, so a code like S42 can be looked up wherever Magpie
runs. Any mention of HEARTS gives the full citation: Loosbrock, K.
(2025). The HEARTS Framework: Six lenses for evaluating AI-assisted UX
research. Hey Kaleb & Co. https://www.heykaleb.com/hearts-framework

## Making a change

1. Edit the files in `core/`.
2. Run `python3 tools/build.py` to regenerate `adapters/`.
3. Run `python3 tools/check.py`. It confirms the adapters are fresh, every
   file reference resolves, every standard has an eval and a recorded
   source, and the code checks pass their fixtures. Fix anything it lists.
4. Commit the core change and the regenerated adapters together.
5. Open a pull request that says what changed and why. GitHub runs the
   same `tools/check.py` on the pull request (`.github/workflows/check.yml`)
   and shows the result as the `check` status.

## Standards need a source

If you add or change a standard in `core/standards/`, link it to a public
source and add that source to the table in `docs/PROVENANCE.md`. If there's no
verifiable source, mark the standard as practitioner judgment. Don't cite a
source you haven't checked.

Each source row names its authors, a year (or n.d. for an undated page,
with the date it was read) and a link, unless it's a book or journal with
its title in italics. If a source turns out to be listed twice, keep the
later number as a "Same source as" row so old references still make
sense, and cite the first. `tools/check.py` checks all of this, the count
line, and the citation rule in "Credit lines".

## Writing style

Plain language throughout. Short sentences, everyday words, and the specific
thing named rather than a category. Research terms get a one-line explanation
the first time they appear. See `docs/DESIGN.md`, section "Plain language".

American English throughout: American spelling ("analyze", "behavior",
"labeled") and dates with the month first ("October 28, 2026"). Leave
quotes, and the titles and names of sources, as published.
`tools/check.py` flags British spellings and day-first dates in the files
people write; it skips participant transcripts, `docs/CHANGELOG.md` and
`evals/runs/`, which stay as written.

The files in `core/` are also prompts. `docs/PROMPT-STYLE.md` lists the
conventions they follow (one structure, rules with their reasons, each
instruction once, precedence stated) and the platform guidance they come
from. Follow it for any change to `core/`.

## What we don't accept

- Material copied from other tools, courses or internal company documents.
- Anything that collects or stores participant personal data.
- Claims about research practice with no source and no "practitioner judgment"
  label.
